SELECT b.booking_id, s.ship_code, a.agent_name
FROM bookings b
LEFT JOIN sailings s ON s.sailing_id = b.sailing_id
LEFT JOIN agents a ON a.agent_id = b.agent_id

01 · How I think

Every dataset starts with four questions.

Building a pipeline is the easy part. My job is making sure the number on the dashboard is right, keeps being right, and actually answers the question being asked.

Q1

Who decides what with this?

I start from the decision, not the table. Regional teams in the US, AU/NZ, and LATAM each read booking data differently.

AI: draft requirements, trace past decisions in email threads
Q2

What breaks it?

Join fan-out, LEFT joins that quietly become INNER joins, missing source keys, and differences between the old and new systems.

AI: review SQL and flag logic risks, but never change logic silently
Q3

How do I prove it's right?

I check row counts, key uniqueness, nulls, date ranges, and sort order, and I diff exports before and after every fix.

AI: write the Python diff and hashing scripts
Q4

Will it survive me?

Every change gets SOPs, reusable SQL templates, and a change log, so the team can run it without me.

AI: generate docs, trackers, and onboarding decks

AI · MigrationRisks caught before prod

AI-assisted SQL modernization for a Snowflake migration

Legacy ODBC queries had to move to Snowflake without changing what the numbers meant.

+Read

Problem

Legacy Crystal Reports and SSMS/Oracle-sourced reports were built on ODBC-escaped SQL with ambiguous columns, and they had to be rebuilt on Snowflake and a new reservation system.

Decisions

  • A repeatable cleanup pattern: Snowflake-native syntax, clean aliases, IN() instead of OR chains, explicit sorting.
  • AI reviews the code and flags issues, but doesn't fix logic on its own. Every change in meaning gets reviewed by a person.

What could go wrong

  • Row fan-out from a missing DATA_SOURCE key when both systems coexist
  • LEFT joins silently becoming INNER joins through WHERE filters
  • Filters that return empty results on the new system's codes

Outcome

A consistent migration playbook the team reuses, with logic risks surfaced before production instead of found by stakeholders.

- WHERE {fn UCASE(a.region)} = 'US' OR {fn UCASE(a.region)} = 'AUNZ' OR … + WHERE a.region IN ('US', 'AUNZ', 'LATAM') -- moved into JOIN … ON to keep LEFT semantics

Transfer descriptions on reports were wrong. Was it the report, or the source data?

+Read

Problem

Booking-level transfer descriptions were wrong after the move to a new reservation system, and stakeholders couldn't tell whether to blame the report or the data.

Proving a production fix with export-to-export diffs

A check-in bug mislabeled bookings, and "it looks fixed" wasn't good enough.

+Read

Problem

A fix and backfill went in for mislabeled check-in bookings. I needed proof that only the intended rows changed.

Decisions

  • Built Python tooling (with AI help) to parse Crystal Reports .xls exports (OLE compound files).
  • Matched records by key, hashed rows, and diffed the exports before and after the fix.

What could go wrong

  • Duplicate keys hiding changed rows
  • Encoding artifacts showing up as false differences

Outcome

The fix was verified at row level, and it became a reusable pre-send checklist: row counts, key uniqueness, nulls, date sanity, sort order, encoding.
